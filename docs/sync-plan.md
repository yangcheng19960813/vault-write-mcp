# 双分支同步实施方案

日期：2026-10-26。状态：本地实现与隔离验收完成。本文保留实施方案与验收记录，正式部署状态另行记录。

## 目标与边界

用户继续在自己的电脑编辑知识库 main；Ubuntu 上 VaultWrite 使用独立普通 Git 副本及 ubuntu 写入分支。服务不断保存有效写入并生成 Git 提交，推送 ubuntu；后台自动合并到 main。合并冲突只阻塞同步，不阻止继续保存和提交。用户在本地将 ubuntu 合入 main、解决冲突并推送后，后台重新评估最新历史并继续同步。

实现阶段限定在本地开发与隔离验收。后续用户已授权发布源码、部署正式 Ubuntu，并恢复 Codex/DSH 接入；QMD 保留独立 main 副本及原有定时增量流程。锚点编辑功能与双分支同步一起发布，无关 .DS_Store 不纳入提交。

## 必须维持的约束

- 写入成功只表示已持久保存，不能宣称已合入 main。文件版本检查、锚点检查、去重回执和原事务恢复继续有效。
- 冲突、网络错误、远端 main 推送竞争不能丢弃已经接收的写入，也不能将实际写入目录留在 Git merge/rebase 冲突状态。
- 禁止 force push、覆盖新提交、丢弃待提交批次、自动选择 ours/theirs、模型自动裁决正文。
- 网络拉取/推送、隔离合并不得持有 Vault 写锁。只在取得快照、校验与应用最终结果时短暂使用现有写锁。跨进程同步另设独立锁，统一锁顺序。
- 仅支持当前服务独占的写入副本；外部编辑、暂存内容、未跟踪文件及不支持的文件类型必须保留并报告，不能自动清理。
- 保留原默认行为：同步默认关闭；关闭时原有提交与 push 语义不变。不引入 Agent SDK、模型请求或额外依赖。

## 同步流程

1. 同步轮次先将已有 interval 批次提交，再在写锁内取得写入分支及提交快照 U。后续到来的写入正常继续。
2. 普通推送 U 到远端 ubuntu，先确保待合并内容可从用户电脑取得。失败则记录错误、下轮重试，继续接收写入。
3. 获取远端 main 快照 M，在隔离 Git 环境尝试合并 M 与 U。可以使用临时 bare Git 库及 merge-tree；不修改真实工作区/index，不执行仓库自定义 merge driver 或 hooks。
4. 无冲突时生成包含双方历史的合并结果 C（已包含或可快进时不制造多余提交），普通推送 C 到 main。main 在期间前进导致推送拒绝时保留所有提交，下轮读取新历史重试。
5. 有冲突时记录涉及的提交、冲突路径和待处理状态；不发布冲突树，ubuntu 保存/提交/推送继续。返回的是 Git 同步冲突，不能放宽单文件版本检查。
6. main 发布成功后，在写锁内重新检查真实写入分支仍为 U、没有新的 pending 批次或外部改动，才将 C 应用到写入副本；否则保留期间新增提交/批次，留到下一轮。
7. 应用整个 Git 快照必须有持久事务与进程中断恢复：正文、删除、Git ref/index 不能因中断长期不一致；沿用 pending.json 的恢复入口，增加明确的事务类型。恢复前验证外部变化，不能强行覆盖。
8. 新增 B、C 等写入后，用户只解决旧提交 A 的 main 不包含新写入；下一轮必须真正合并最新双方历史。无冲突继续同步，有冲突继续待处理，不得 reset 到只含 A 的 main。

流程对冲突类型不作“必能自动解决”的保证。非文本、删除/修改、重命名等冲突必须可靠阻止发布。应用不支持的文件类型或路径拓扑时，清楚报告受阻并保留写入，而非静默遗漏或修改已接收内容。

## 配置与操作入口

- 新增 `[sync] enabled = false`、`main_branch = "main"`。
- 沿用 `[push] enabled`、`remote` 及现有检查周期 `commit.interval_seconds`。开启 sync 要求 push 开启；写入分支与 main 不同，push.branch 为空或等于当前写入分支，拒绝误配置到 main。
- 不自动切换或创建服务所在分支。文档给出独立测试 clone/分支准备方式。
- 后台 worker 接入同步轮次。提供 CLI `sync` 与 `sync-status`；原 flush/push 路径在开启 sync 时协调一致。
- MCP 只增加只读 `sync_status`，展示最后一次同步结果及当前写入提交、待提交数量，区分已保存与已发布。状态读取不触发网络或模型请求。
- 冲突状态包含有限长度的路径列表、双方快照及统计；错误状态包含可诊断的阶段/错误码，不能持久化凭据或 URL 中的认证信息。

## 可观察验收

全部使用临时 bare 远端、模拟本地 main 副本与 Ubuntu 写入副本验证：

1. 双方无冲突修改自动合入 main，写入副本取得合并结果；空轮次不重复创建合并提交。
2. 同一行冲突：main 不变，ubuntu 的提交可拉取，随后仍可继续有效写入、提交及推送；实际笔记无冲突标记。
3. 用户本地解决冲突并正常 merge/push main 后，Ubuntu 自动接续，保留双方内容与祖先关系。
4. 处理冲突期间 Ubuntu 又产生新提交：既覆盖干净合并，也覆盖再次冲突；新提交不得丢失。
5. 同步网络或合并被暂停时，另一个真实线程/进程仍能完成写入；新增 immediate 提交和 interval pending 均不得被旧快照覆盖。
6. main 在预检/推送期间前进，普通推送拒绝后可重试，保留远端新提交；网络错误和重启不会重复写入或反复提交同一批次。
7. 同步应用事务在准备、文件部分写入、ref/index 更新等阶段实际进程退出，重启可恢复；外部修改不得被恢复程序覆盖。
8. 多进程同步互斥；误配置、外部暂存/未跟踪碰撞、删除/修改及不支持文件类型得到明确结果；不破坏原有版本/锚点/批次/HTTP 测试。
9. 配置加载、worker、CLI 与真实 MCP 状态接口贯通。给出完整测试命令及真实结果。
